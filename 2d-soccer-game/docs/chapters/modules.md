# 模块卡片：从功能找到源码

读卡片时先看“问题”，再做算例，最后改代码。A 的行号均指本仓库不变的 `reference/projectA/` 快照；B 的库/图用 SLX 内部路径标识，因为二进制文件没有可靠文本行号。迁移文件可能因新增注释而变行，优先按函数名导航。逐模块的实际文件与行号由脚本生成，见 [源码对应表](../generated/source_map.md)。数值计算示例的可复现结果集中在 `docs/generated/manual_numbers.json`，模型轨迹在对应 evidence 回执中。

## goToPose：到一个位置应该请求多快？

- 原理与算例：目标越远，比例控制给的速度越大；原始第一拍前锋距接近点 0.55 m，Kp=0.8，前向请求 0.44 m/s。它是请求，仍需执行侧限速。
- 源码：`algorithms/+tdp/goToPose.m`，源自 A `goToPose.m` 全函数；角度归一化在 `tdp.angWrap`。输入自身位姿、目标点/朝向、8 个观测机器人、自身索引、球、绕球开关、P；输出 1×3 车体命令。
- 手动：运行 baseline 首拍命令，再将目标 x 移远，比较请求而不是积分后位移。
- 测试：`test_algorithms/testGoToPose` 1000 组；阈值扩展示例另测。
- 修改：改增益或避障项之前保留原式，添加一个能区分新旧行为的场景。限制：局部几何避障不是全局路径规划，不保证走出对称死锁。

## kickSkill：球在附近为什么还不能踢？

- 原理：必须同时满足到球距离、朝向误差、站在球后方、冷却完成和 allowKick。否则先绕到球后，再向球迈近。默认 robotR+ballR+0.06=0.28 m 是几何触发范围。
- 源码：`algorithms/+tdp/kickSkill.m` 对应 A 同名函数；唯一随机接口改动是传入 noiseSample，函数自己不抽样。输入目标、速度、观测、P、标准正态样本；输出命令、是否可踢、候选二维球速。
- 手动：机器人 (-0.25,0,0)、球 (0,0)、目标 (4.5,0) 可触发；转身 pi 后应先转向。候选球速由环境采用，Core 不写物理球。
- 测试：1000 组包含至少 100 个实际踢球分支，旧函数 RNG 样本与新接口逐个配对。
- 修改：阈值改动要检查刚内/刚外边界。限制：几何可踢不等于三维脚已经碰到球。

## robotModel：0.44 m/s 请求为何只走 0.0125 m？

- 原理：前后/侧向速度上限不同；先按速度椭圆缩放，再转场地坐标、按 dt 积分，并限制外缓冲边界。
- 源码：`algorithms/+tdp/robotModel.m` 对应 A 同名函数；输入 1×8 机器人、8×3 命令、P，输出机器人。
- 算例：前向 0.44 被限为 0.25，50 ms 位移 0.0125。theta=pi/2 时相同车体前向命令增加场地 y。
- 测试：1000 组数值等价。改动：速度上限保留“估计”来源，测得 NAO 数据后再标定。限制：没有步态、加速度、倾倒、足底接触。

## ballModel：为何停止距离不是连续时间公式？

- 原理：先扣 `ballDecel*dt`，再用新速度积分。因此 1.8 m/s、0.4 m/s²、dt=0.05 的 90 步行程是 4.005 m。
- 源码：`algorithms/+tdp/ballModel.m` 对应 A 同名函数；输入/输出 BallBus 和 P。
- 手动：以结构体初始化球，循环调用 90 次。若得到 4.095，通常是先积分再减速；若是 4.05，可能用了连续公式。
- 测试：`test_baseline/testRolling` 与 1000 组等价。限制：二维恒减速度是估计，非材料摩擦实测。

## collisions / Contact2D：圆形代理重叠怎么办？

- 原理：A 的两两分离只做一轮且跳过中心重合，必须先复现再改变。`tdp.collisions` 保持原行为；`Contact2D` 按 rulesProfile 选择修复。
- 源码：A `collisions.m` 机器人段 4–15 行，球接触段 17–34 行；迁移环境在 `environment/Contact2D.m`。
- 输入/输出：机器人、球、裁判、球是否活动、活动槽位、P；返回物理状态。算例：两个半径 0.15 m 的同心圆，修复后间距至少 0.30 m（容差见测试）。
- 测试：1000 组兼容等价；`test_source_defects` 证明旧行为；`test_repairs` 检查同心、三圆链、边界八圆与非活动槽位。
- 修改：改迭代上限时同时检查最坏残差和 600 s 指标。限制：几何投影不保存真实动量，球多点接触仍是简化模型。

## rulesCheck / Referee2D：球出界后归谁、放哪？

- 原理：是否进球先看整球越门线，再看门框内条件；得分队按球门端决定。A 的出界重开站位是简化规则，不能自动当作 RoboCup 标准。
- 源码：`tdp.rulesCheck` 对应 A `rulesCheck.m` 全函数；环境 `Referee2D` 添加可选规则配置。输入机器人、球、裁判、P；输出重置后的状态。
- 算例：球 x=-4.6、y=0，无论 lastTouch=0 还是 1，红队得分；参考球门球放在 (0,±3)，ACompat 放在 (±3.5,±1.5)。
- 测试：1000 组兼容等价、乌龙/无人触球/重开位置/对手距离回归。
- 修改：每项规则先标来源类别与适用比赛类别。限制：没有完整罚球、犯规、间接任意球两次触球判定、比赛管理器协议。

## roleAssignment：谁当这一步的前锋？

- 原理：候选场上球员的代价包含到球距离、转向误差、是否越过球；老前锋只要没有差到超过 roleHyst，就保持角色，减少频繁切换。
- 源码：`tdp.roleAssignment` 从 A `teamBehaviour.m` 21–44 行提取；输入观测机器人、球、队号、上拍前锋记忆、P；输出 1×4 角色和新记忆。
- 算例：两人代价 1.0 与 1.2，旧前锋是后者且余量 0.4，会保持旧前锋。代价差超过余量才切换。
- 测试：1000 组，对照 A 输出角色和记忆。改动：固定前锋示例放在 TeamCoordinator 的显式开关，兼容算法不改。限制：集中式全场角色分配，需要课程许可与通信策略。

## actionSelection / laneClear：射门、传球还是小踢？

- 原理：前锋离对方球门近时射门，否则优先小踢；支持者位置合适且传球段附近没有对手时可传球。laneClear 计算障碍点到线段的最近距离，不是到无限直线的距离。
- 源码：`tdp.actionSelection` 对应 A teamBehaviour 45–96 行（构造函数在 99–105 行）；`tdp.laneClear` 对应该文件最后的局部函数。输入 8 机器人/球/角色/P；输出 4 Intent；laneClear 输入 a、b、4×2 对手位置、margin，输出布尔。
- 算例：线段 (0,0)→(2,0)，障碍 (1,0.3)、margin=0.4，线路不通；障碍 (3,0.3) 应按端点 (2,0) 算距离。
- 测试：各 1000 组与原函数比较。改动：给新动作独立枚举和测试。限制：无预测拦截、无遮挡相机模型、接球队员未做闭环协作。

## TeamCoordinator：为什么不是每个机器人各选一个前锋？

- 原理：每队一个协调器保存一个前锋记忆，四个计划共享一致角色。每台机器人仍单独执行技能。
- 源码：`controllers/TeamCoordinator.m`，A teamBehaviour 的角色/动作拆分；B 只提供“总线+枚举”的结构启发，不复制状态条件。
- 输入：ObservationBus、team、previous、P。输出：1×4 Intent、striker。例：蓝队 mem=4 与红队 mem=4 是各自的本队 4 号，不是同一个世界索引。
- 手动：在 tdpMatch 中跟踪 Team1StrikerMemory 和 Team2StrikerMemory。测试：角色 1000 组、比赛逐步比较、角色扩展示例。
- 修改：增加团队记忆时用独立延迟和初值。限制：初版团队观测是理想全局观测；失球后的团队策略可继续完善。

## Observation2D：把真值变成控制器允许知道的量

- 原理：环境真值与观测接口分开；数值不变但有效性、采集时间和视野可以改变决策。
- 源码：`environment/Observation2D.m`，新设计；未继承 B 的负数位置哨兵。输入世界、自身索引、tSim、P；输出 ObservationBus。
- 算例：世界状态时刻 1.00 s，在 1.05 s 调用时 robotStamp=1.00，而非伪造为 1.05。FOV=pi/3 时身后的球无效。
- 测试：`test_actuator/testObservationAcquisitionTime`、观测不变而真值改变的回放、有限视野扩展。
- 修改：噪声/延迟在适配层加入，不能偷偷修改控制器收到的时间。限制：理想定位和全局机器人列表，不是相机识别。

## CoreGeometry / EmitRequest：把数值算法接到状态图

- 原理：Geometry 先检查观测年龄，再算接近速度和 ready；EmitRequest 根据阶段生成请求。compat 的即时路径是明确的等价开关。
- 源码：`controllers/CoreGeometry.m`、`EmitRequest.m`；新设计，调用 A 迁移算法。
- 输入：观测、意图、tSim/P；或几何量、阶段、编号、锁定目标/时刻/P。输出：GeometryBus / RequestBus。
- 算例：采集 1.00、当前 1.55、最大年龄 0.50，自身失效则 Stop。测试：回放、迟到反馈、无真值输入、行走期限。
- 修改：字段变化同步更新模板、字典和建图脚本。限制：只有二维全向速度语义；三维执行层需解释如何实现请求。

## ControllerCore：管理持续动作的生命周期

- 源码：`scripts/build_controller.m` 生成 `models/ControllerCore.slx` 的 Core；新状态逻辑，B SoccerBehavior 只作 Stateflow 组织参考。
- 输入：观测、团队意图、反馈、tSim；输出：请求和诊断 phase。完整状态文字、优先级和周期算例见 Stateflow 章。
- 手动：先做平铺图，再嵌套 Active，再加入编号和超时。测试：`test_controller` 的实际 Stateflow 回放及单机闭环，两个周期。
- 修改：在脚本中改状态文字/转换，再重建所有库引用模型。限制：requestId 重启后的跨会话协调尚未实现；需要部署时的会话身份。

## Actuator2D：重复请求会不会踢两次？

- 原理：保存已接受编号和当前动作；相同编号返回同一执行过程。准备到期后重新确认球是否还在可踢位置。
- 源码：`environment/Actuator2D.m`，新协议实现。输入内部记忆、Request、Observation、tSim、P、仲裁允许、噪声样本、故障注入；输出新记忆、反馈、速度、doKick、候选球速。
- 算例：编号 12 在 2.00 与 2.05 s 到达，executions 只加 1；2.20 s 完成准备或失败。测试：`test_actuator`；故意把 `>` 改 `>=` 的变异确实导致重复执行测试失败。
- 修改：新增执行动作要定义接受、进行、结束、失败和取消语义。限制：二维准备时间是教学设定，不能当作 NAO 踢球耗时。

## Plant2D / MatchPlant2D / KickArbiter2D：谁真正推进比赛？

- 原理：环境统一拥有物理状态和 RNG。仲裁在同拍只选择第一个满足条件的人；物理更新仍按 A 的顺序。
- 源码：`environment/` 三个同名文件，对应 A 主循环 20–67 行的环境部分。输入 World、请求、计划、tSim/P，输出 World 和反馈；仲裁输入观测/计划，输出允许标志。
- 算例：同时可踢的 1 与 5 号，奇数步允许 1，偶数步允许 5。测试：比赛奇偶仲裁测试及真实变异；完整 40 场逐步比较。
- 修改：不得把一个 Core 的请求直接连到 BallBus 真值字段。限制：compat 仲裁仍依赖理想观测下的一拍即时执行；三维运动可能失败，不宜当作队伍策略直接复用。

## Viewer2D：显示不能改变比赛

- 原理：绘图读取已经保存的轨迹；关闭它应不影响数值结果。
- 源码：`environment/Viewer2D.m`，新离线显示；A viewer 作为视觉范围参考。输入 98 列轨迹、步号、P、可选图片路径，输出不可见 Figure。
- 手动：`f=Viewer2D(trace,100,P,'build/view.png');close(f)`；图中蓝队攻 +x，机器人箭头表示朝向。图片由生成脚本写入 docs/generated。
- 测试：手册生成与数值一致性测试。修改：只改显示层。限制：单张快照不是时间回放动画，也不是碰撞验证。

## tdpRun / runA / 构建脚本：怎样留下可复查的运行？

- `runA` 是冻结旧逻辑的 oracle（参照实现），覆盖练习参数但不改原文件；`runMatch` 运行实际八实例模型；`tdpRun` 保存配置、轨迹、指标与耗时。
- 所有新 SLX 从空白由 build 脚本产生。`tdpSetup` 只改当前 MATLAB 进程路径和缓存目录；不调用 savepath，不操作已开的桌面。
- 新的输出目录用于每次尝试；大 MAT 留在 build 并在证据中记录 SHA-256。失败日志不能覆盖。
- 测试：一键复现、基线确定性、干净 clone。修改：先验证新参数，不给 null 默认填零。限制：不同 MATLAB/编译器版本可有末位浮点差异，必须重跑数值门限与指标比较。
