## 先看十秒比赛

在桌面终端进入工程根目录后运行以下两行。默认一个蓝队向右、一个红队向左。首次启动会编译模型，场地出现后等计分板下的仿真时钟开始走。

```bash
cd '/home/fayne/Documents/Robotics & AI/Robotics TDP/2d-soccer-game/tdp-migrated-r1'
TDP_2D_DURATION=10 TDP_2D_SPEED=1 ./start_2d.sh
```

在窗口中选 Pause，观察仿真钟停住。选 Resume 继续。默认控制周期 0.05 s，完整十秒应保存 200 拍，关窗后终端退出。赛后查看窗口或终端列出的 `build/animation-…/receipt.json`，同目录 `trace.mat` 保存 `trace`、`tactics` 和 `P`。在另一台机器上按[实时动画启动章节](live_animation.md)先检查 MATLAB 路径和图形会话。若只见场地没有运动，先看编译状态、是否暂停，再查回执状态和首条报错。

已有 MATLAB 桌面中，把 Current Folder 切到工程根目录，可直接传入参数。下面用 0.04 s、8 倍速观察模型。倍速只影响墙钟显示。

```matlab
tdpSetup;
P = tdp.v1Config();
P.dt = 0.04;
P.Tmatch = 10;
app = start_2d(P,8);
```

## 1. 四个人怎样围绕一个球配合

先看蓝队进攻的一个瞬间。球在场心右侧，4 号前锋得到追球授权。3 号中场走到前锋身后偏侧，2 号后卫留在己方半场，1 号门将面对球在门前横移。4 号发生已确认的执行故障时，3 号可以临时顶上。记录里 3 号的角色始终是中场。变化的是谁负责下一次接近、对齐和踢球。

**主追球者**指协调器指定可以主动接近足球、抢球或射门的人。防守者站到球和球门之间拦截线路，也可能被滚来的球碰到。可用追球授权、意图与实际执行请求区分主动追球和被动接触。每队每拍允许零人或一人主动追球。

| 每队本地号〔工程配置〕 | 固定身份〔球队 V1〕 | 进攻时 | 防守或未知球时 |
|---|---|---|---|
| 1 | GK，守门员 | 留守门前，随已知威胁调整横向位置 | 已知球时保护射门线路，未知球时守门中央 |
| 2 | DF，后卫 | 留在己方半场，挡住快速反击的路线 | 保护门前空间，移动到威胁线路上进行区域拦截，未知球时保持防线 |
| 3 | MF，中场 | 去 ST 身后或侧方，准备争第二落点 | 回撤封中央，仅在获指定时争球。未知球时回中央。ST 不可用时临时接管进攻 |
| 4 | ST，前锋 | 搜索、接近、对齐并尝试射门 | 常规防守时留出反击接应点，未知球时负责搜索 |

蓝队全局编号为 1–4，红队为 5–8，红队 7 号是本队 MF。组员先在纸上写一次双队编号，再对照开球站位。若红队跑向蓝队身后相反的空间，先查场地方向。蓝攻 +x，红攻 −x，正 y 及角度沿用工程接口。[开球位置，第 3 行](../../algorithms/+tdp/kickoffReset.m#L3) · [坐标约定](interfaces.md)

## 2. 半场判断与动作交接

### 一拍的输入、判断和输出

一拍是一个控制周期。每队协调器读取本拍允许使用的观测、比赛许可、人员可用性，以及**上一拍实际发出的请求与对应执行反馈**。个人 Stateflow 状态图处理 Search、Approach、Align、Kick 和 Recover。团队协调器负责攻防、任务分配与接管。环境执行层负责接触和球速。回路中各用一拍的 Unit Delay 保存团队记忆、实际请求和反馈，防止同一拍结果反过来影响本拍判断。

当前协调器按下表执行。第一列从上至下判断，排在上面的情况优先。*基础攻防状态*只记录最近一次从有效球观测确认的 ATTACK 或 DEFEND，球暂时不可见时可保存这一记忆供重新判断。表中的选人、初始状态及失败锁存方式是**V1 的工程教学设定**，组员可以修改后重新验收。

| 优先级与条件 | 对外状态 | 本拍任务与交接 |
|---|---|---|
| 1 裁判停赛 | 暂停执行 | 撤销所有动作许可，有活动踢球则发同编号 Stop 取消。保留固定身份及暂停原因 |
| 2 球无有效观测、采集时刻在未来或已过期 | SEARCH/HOLD | 正常由 ST 搜索，MF 回中央，DF/GK 守位。ST 不可用时由健康 MF 接管搜索。两人均不可用则保持阵型。关闭全队踢球许可 |
| 3 球已知，ST 不可用或其实际进攻请求收到匹配的 Failed | FALLBACK | MF 可用时独占进攻任务，否则不授予追球。DF/GK 维持防守。保存进入原因与失败编号 |
| 4 球已知、ST 可用且没有待恢复故障 | ATTACK 或 DEFEND | 由确认半场决定。ATTACK 指定 ST，MF 支援。DEFEND 下 ST 准备反击，MF 优先封中央，仅当协调器明确指定其争抢近处自由球才追球。DF 保护门前 |

**接管的退出条件**是 ST 已显式恢复，且 MF 的旧动作已结束或取消并收到匹配终态。每拍先用上一拍的新反馈更新这两条记忆，再按 1–4 选择动作。若恢复后进入正常防守，按 DEFEND 分工。停赛始终优先。若球不可见且 ST 故障，外显模式为 SEARCH/HOLD，另记接管原因和实际搜索者，避免把一个条件覆盖掉。

**有效观测**要求球或机器人的有效标志为真，位置和采集时刻有限，采集时刻不晚于 `tSim`，数据年龄在许可范围内。在二维理想传感器中，协调器从本队四名机器人的新鲜有效观测选最近采集的一份，同一时刻按本队编号打破平局。所有观测失效即走未知球分支。个人机器人还须检查自己的定位、当前球观测与动作许可。

**失败判定**先比机器人编号，再比该机器人发出的 `requestId`、动作类别及有效时间窗。仅将已授权的进攻动作的有效 Failed 记为执行失败。去重后同一请求只处理一次。Running 表示正在执行，Done 表示执行层结束，Rejected 单独记拒绝原因。无反馈达到超时阈值，可先停止本次动作并记录超时，当前配置用匹配 Failed 或显式不可用触发接管。撤权导致的取消反馈要关联本拍 Stop，避免将正常交接误算为新的故障。

**准备中的踢球**可能已经由个人状态图保留了原来的目标和编号。应在八个个人请求汇合之后再检查本拍授权。在撤权、失球、停赛时，把仍待执行的旧 Kick/Tap 以同编号 Stop 送入执行层。非追球者的合法守位 Goto 应继续。以实际交给执行器的请求和反馈检查结果。V1Plant2D 还会结束已从物理场景移除的机器人的活动动作。仅注入可用性故障时，物理身体仍在场，按正常 Stop 路径退出。

### 参数怎样改变分工

程序生成的表逐项列出 V1 增加或覆盖的参数，包括默认值、类型、尺寸、单位和来源。表中也列出全部 11 个团队记忆字段和 171 列战术记录。从 MATLAB 执行 `export_v1_contracts` 可以重新生成并用手册测试核对。[可读参数与接口表](../generated/v1_contracts.md) · [完整配置 JSON](../generated/v1_config.json)

中线半宽 `v1MidlineBand` 为 0.15 m，边界相等时维持原基础相位。双方自由开球时初态 Attack。角色编号和开球约定均为工程教学设定。门将站在距己方门线向场内 0.35 m 处，以球的横向坐标 y 的一半作为门前横移目标，限制在两门柱内并预留一个机身半径。后卫以己方球门为起点，沿威胁方向选防守点，限制在本方半场。中场在进攻时从 ST 身后 0.70 m、两侧 0.80 m 的候选位中选择较空一侧。两点同样空时选球队坐标的左侧。

防守时，中场封中央。仅当中场距球不超过 1.20 m、球速不超过 0.35 m/s、所有对手位置都新鲜且各自距球严格大于 0.60 m 时，中场才获准争球。中场在此情景获准追球属于正常 DEFEND。战术日志中的 `takeover` 单独表示 ST 故障或不可用后的临时责任。

**接管只由显式恢复信号解除。** 正常比赛将故障/恢复窗口全部设为零。如果实际 ST 踢球收到匹配 Failed，MF 的接管可能延续到终场。ST 再次看见球、等待几秒或重新变为可用，都不构成恢复命令。组员可在定向实验中使用 `v1RecoveryWindow` 注入恢复，另行报告自然比赛的接管占比和定向恢复结果。

### 用五个采样走过中线

设蓝队上一确认状态为 DEFEND，球观测均新鲜，步长 0.05 s。每次只用本行输入与上行状态作判断。

| tSim (s) | 球 x (m) | 蓝队预期 | 理由 |
|---:|---:|---|---|
| 1.00 | −0.20 | DEFEND | 超过己方侧边界 |
| 1.05 | +0.04 | DEFEND | 位于滞回带内 |
| 1.10 | +0.16 | ATTACK | 确认进入对方半场 |
| 1.15 | −0.10 | ATTACK | 小幅回摆仍保留上次确认 |
| 1.20 | −0.16 | DEFEND | 确认回到己方半场 |

红队可把同一张表的 x 全部取反，初态同设 DEFEND，逐行结果应相同。若按同一场地坐标回放原表，红队的前进轴方向相反。下表的输入也送入当前协调器，输出由脚本生成，可对照[实际回放](../generated/v1_contracts.md#中线五拍回放)。

### 一次动作交接应怎么看日志

以下各场景独立。#41、#42 是教学编号。每个机器人有自己的编号序列，同号跨机器人不能相互匹配。可将演算与两个周期的实际测试日志并排查看。[模型接线与真实交接时间线](v1_model_interface.md) · [运行生成的事件表](../generated/v1_model_events.md)

| 场景 | 输入时间线（均为仿真时间） | 预期观察及首查项 |
|---|---|---|
| 常规进攻 | 2.00 s 已确认蓝 ATTACK，ST 位于可踢位置，发 #42。执行器返回 Running。2.20 s 准备满，条件仍满足 | 仅 ST 可踢，#42 执行一次。分别记录终态、实际施加踢球事件与球速变化。若一直不踢，查朝向、冷却及仲裁许可 |
| 球位置未知 | 3.00 s 有效标志变假。另做两份回放，藏在失效记录里的球坐标分别为 (4,2) 和 (−4,−2) | 两份团队计划和有效请求逐拍相同，ST 搜索，MF/DF/GK 保形。补一组把标志改真作为阳性对照。差异先查协调器是否先读了球坐标 |
| 观测过期 | 同一份采集时刻 4.00 s 的球观测在 4.50 s、4.55 s 到达。其余输入有效 | 按 0.50 s 例值，前者刚好有效，后者转 SEARCH/HOLD。另测未来和非有限采集时刻 |
| 匹配失败 | 5.00 s ST 发 #42，5.05 s 协调器读到上一拍的 ST/#42/Failed，反馈时间处于有效窗口 | 进入 FALLBACK，MF 身份保留。重复投递该反馈，接管次数仍为一次。查实际发送编号及每机器人匹配 |
| 迟到反馈 | ST 当前有效请求为 #42，5.05 s 输入上一请求 #41 的 Failed，再输入另一机器人 #42 的 Done | 两条均不结束 ST/#42，也不触发 ST 故障。查日志是否同时保存了机器人编号与请求编号 |
| 撤权 | 6.00 s ST/#42 开始准备。6.05 s ST 失去授权，MF 接管，个人状态图本拍仍可能输出旧 Kick | 授权层送给 ST 执行器的是 Stop/#42，旧请求不能在 6.20 s 踢球。MF 只能从自己的观测与技能状态产生新请求。若见两次执行，先查实际请求是否绕过授权层 |
| 恢复 | 7.00 s ST 被标记恢复，此时 MF/#17 正在准备。先对 MF 保留编号进行取消，下一拍确认终态 | 交接期间至多一个授权。MF 释放后按当前相位重新分工，迟到 MF/#17 不影响之后的 ST 请求。若冻结，查物理移除是否跳过了取消 |
| 停赛/无反馈 | 分别在准备中撤去比赛许可，或持续缺反馈达 1.00 s | 停赛时所有有效请求停止。超时须记录具体机器人、请求、仿真时刻和退出技能阶段，禁止将“无消息”记录成 Done |

## 3. 一拍的接线和状态所有权

模型生成入口为 `build_v1_match`。它读取 `tdp.v1TeamMemory()` 创建独立 `TdpV1Types.sldd` 中的 `V1TeamBus`，引用公共字典，再调用比赛构建脚本从空白生成 `tdpV1Match.slx`。改结构时修改构建脚本、复建模型、运行测试，并一并提交脚本和生成结果。[建模入口](../../scripts/build_v1_match.m) · [八实例接线](../../scripts/build_match.m)

| 执行顺序 | 信号与操作 | 人工检查方法 |
|---|---|---|
| 1 物理状态经观测适配器 | WorldMemory 供给 V1Observation2D，产生 1×8 个带采集时刻的观测。不可用、失明、过期与停赛窗口在这里注入 | 改变失效观测中的球位置，确认同一拍的有效请求完全一致。[观测适配器](../../environment/V1Observation2D.m) |
| 2 两个独立协调器 | 每个协调器接 1×8 观测、本队记忆、上一拍有效请求与反馈、显式恢复布尔量，输出 1×4 Intent 和本队新记忆 | 查 `basePhase`、`phase`、`chaser`、`ballSource`。每队一份 Unit Delay 防止本拍结果直接回到输入。[协调器](../../algorithms/+tdp/v1TeamPlans.m) · [记忆初值](../../algorithms/+tdp/v1TeamMemory.m) |
| 3 八个个人 Core | 外层仲裁安排每步至多一次踢球，个人状态图根据本人的观测和反馈决定 Search、Approach、Align、Kick、Recover | 从球是否新鲜、朝向、距离与冷却检查进入 Kick 的条件。[个人状态图](../../scripts/build_controller.m) |
| 4 有效请求经过授权 | JoinRequests 后比对本拍追球人、球有效性、计划、比赛许可、有效期。若先前动作仍 Running，撤权要送同编号 Stop | 将 `rawKind`、`kind`、`rawId`、`requestId` 并排观察。MF 交还时会出现原始 Kick 被送成 Stop 的一拍。[请求授权](../../environment/V1AuthorizeRequests.m) |
| 5 环境执行与反馈 | Actuator2D 准备并去重，V1Plant2D 处理故障窗与动作完成。只有环境更新球速与比分 | 看 `kicker`、`status`、`feedbackId` 及物理轨迹，区分请求、失败、执行和球实际移动。[执行适配器](../../environment/V1Plant2D.m) · [执行器](../../environment/Actuator2D.m) |
| 6 延迟与记录 | 新物理状态、每个实际请求、反馈和每队记忆分别进入延迟元件，供下一拍使用。时钟来自 tSim | 检查代数环诊断为 error，物理轨迹与战术日志逐行时间戳相同。[战术记录器](../../environment/V1TacticsRecord.m) |

队级函数的四个输出意图按本队本地号 1–4 排列。八个输入槽和日志 `chaser` 始终使用全局号 1–8。固定角色枚举为 GK=1、ST=2、DF=3、MF=5，旧 SP 的编号 4 保留给迁移基线。V1 的一队角色列因而是 [1,3,5,2]。团队相位枚举 Hold=0、Defend=1、Attack=2、Search=3、Fallback=4。个人技能枚举、动作枚举和反馈状态都有各自的定义，数值相等时仍要按所属字段解释。[团队相位](../../interfaces/TdpTeamPhase.m) · [公共接口](interfaces.md)

### 怎样查两种相同拍数的日志

`trace` 是更新后的物理状态和比赛统计。第 49–56 列是八个机器人的角色，第 57–60 列是球 x、y、vx、vy，第 61 列是仿真时刻，第 62–63 列是比分，第 66–67 列是射门，第 97 列标记该拍确实踢球。**在 V1 比赛中，第 71、72 列分别是蓝、红队本地追球者编号**，0 表示该队无人获权。红队本地 3 号对应全局 7 号。旧 ACompat 在这两个位置保存该队当时的本地前锋编号。读轨迹时先确认模型和 `P.v1Enabled`。[98 列格式](../../environment/MatchRecord.m) · [本地编号换算](../../scripts/build_match.m#L101)

`tactics` 是同一拍的 171 列战术记录。位置和观测来自上一拍物理状态，动作/反馈及 `kicker` 属于本拍执行。优先用列名字典，避免复制列号。以下三行在已有的 `trace,tactics,P` 上运行。每个实际踢球事件输出仿真秒数和全局机器人号。输出可为空，表示该次运行还没有实际踢球。

```matlab
c = v1TraceColumns();
k = find(tactics(:,c.kicker)>0);
disp([trace(k,61), tactics(k,c.kicker)])
```

要解释某个动作，从 `intent → rawKind → kind → status → kicker` 顺读，再查看球的速度/位移。仅有 Done 表示执行器宣告结束。仅有球移动也可能源自接触或裁判重置。V1 整场报告分别计实际踢球、达到射门速度的实际射门、MF 实际射门和比分。[完整列号和单位](../generated/v1_contracts.md) · [指标计算](../../scripts/v1MatchMetrics.m)

## 5. 自己改一个场景并验证

1. **先读技能与团队各管什么。** 打开 `tests/test_v1_tactics.m` 的 `testBoundaryAndHysteresis` 和 `testPendingKickMustReleaseBeforeRecovery`。先预测每拍模式、追球者和退出条件，再对照函数输出。重点看“MF 身份”与“临时追球权”的不同。[函数台架](../../tests/test_v1_tactics.m)
2. **引入真实个人 Core。** `test_v1_model` 在八机器人模型中把初始球和机器人布到可踢位置，把不可用窗口放在踢球准备之后。读取 `rawKind`、`kind`、`status`、`kicker`。丢球或撤权时若旧编号仍踢出，先查请求是否经过授权层。[模型场景](../../tests/test_v1_model.m)
3. **亲手改故障和恢复。** 用下方十秒案例查看蓝 ST 暂时不可用、蓝 MF 接管、恢复信号到达三者的区别。要改红 ST，窗口行号是机器人 8，恢复窗口行号则是球队 2。想观察“MF 正在踢球时恢复”，使用模型套件中的定向布置和 `testRecoveryDrainsPendingMidfielder`。
4. **验证整场指标。** 先运行三个 V1 套件，再运行 20 种子 × 0.05/0.04 s × 600 s。每个种子分别有 12,000 或 15,000 拍。检查每场版本、源指纹、参数、退出状态、轨迹哈希及失败片段。0.05 与 0.04 是各自独立的积分周期，分别验证确定性。正式命令在本章开头。
5. **保存和排错。** 组装最终回执时检查 40 个唯一的种子/周期组合、两种周期种子 1 的重复运行、固定角色、授权/执行不变量和物理有限值。将无触球场次记作“未发生”。记录越比赛区与越外缓冲界、重叠、完全受阻平移采样比例。缺日志、未完成或失败的场次保留状态，不合并为通过。比较策略成绩还需同初态、规则、执行模式和噪声的配对组。[矩阵入口](../../scripts/validate_v1_matrix.m) · [验收回执检查](../../scripts/v1_matrix_evidence.py)

```matlab
tdpSetup;
P = tdp.v1Config();
P.Tmatch = 10;
P.v1UnavailableWindow(4,:) = [2 4];
P.v1RecoveryWindow(1,:) = [5 6];
[trace,tactics] = runMatch(P);
c = v1TraceColumns();
rows = tactics(:,c.time)>=1.95 & tactics(:,c.time)<=5.10;
disp(tactics(rows,[c.time c.phase(1) c.chaser(1) c.takeover(1) c.recovering(1)]))
```

2–4 s 之间蓝 ST 不可用。4 s 时它恢复可用，已锁存的接管仍然有效。5 s 起团队收到显式恢复，若 MF 有待完成动作则先撤权并等待匹配终态。分析输出时同时查裁判暂停、球是否可见和 ST 是否已经另有匹配失败。各时间窗是确定性教学注入，默认整场比赛关闭。

本例已在独立 MATLAB 进程复现。撤去蓝 4 号的可用性后，蓝 3 号接管。4 s 时蓝 4 号重新可用，接管仍保持。5 s 发出恢复信号后，协调器回到 Defend，当拍的主追球者为 0，前锋准备反击。另一场 0.04 s 的十秒比赛通过 `tdpRun` 保存并重新载入，物理与战术矩阵分别有 250 行。[实际命令与 MAT 哈希](../../evidence/tactics-v1/handson-01/command.json) · [逐时刻读数与回执](../../evidence/tactics-v1/handson-01/receipt.json)

配置错误通常会在启动之前报出。`TDP:V1Mode` 表示 V1 需要 Delayed 执行模式。`TDP:V1Window` 优先检查起止顺序、队 2 行还是机器人 8 行。要调几何阈值，复制 `P=tdp.v1Config()` 后改实例，例如改变 `P.v1MidlineBand`，再执行 `tdp.validateV1Config(P)`、复跑中线台架并记录差异。更换实现时保留原 ACompat 基线入口 `runMatch(tdp.defaultConfig())` 与对照检查。
