# 独立复现指南

读者：有软件工程背景的机器人方向硕士生。目标：读完本文后，**不看参考实现的源码**也能写出功能等价的回放、事件和导出，并能自己写测试来证明。参考实现只用来在最后比对差异。

## 2. 问题分解

目标不是“放一遍比赛”，而是“能回答行为问题”：为什么前锋在等？谁在什么时候被授权追球？请求发出后机器人是否真的动了？所以分成六层，每层只依赖前一层，可以逐层写、逐层测：

```text
(1) 载入与校验    文件 → rec            关心：坏文件、缺字段
(2) 时间索引      时间 t → 行号 k       关心：浮点、边界
(3) 渲染一行      行 k → 画面            关心：不改数据、可重复
(4) 播放状态机    墙钟 + 速度 → t → k    关心：暂停/换速/跳转时时间连续
(5) 事件          矩阵 → 事件列表         关心：记录 vs 推断
(6) 导出          行区间 → MP4 + 对照表   关心：按行渲染、时间对照
```

先写 (1)(2)(5)——它们不需要窗口，最容易被自动测试，也最能暴露你对数据的误解。

## 4. 算法与数据变换

### 4.1 按时间找行（层 2）

记录时间 `times(1..N)` 严格递增。给定秒数 `s`，要的是“不晚于 s 的最近一行”：

```text
k(s) = max { j : times(j) ≤ s + ε }，若集合为空则 k = 1
```

`ε` 是容差。时间由 `dt` 累加而来，`times(3332)` 实际是 `166.60000000000002`；若直接用 `≤ 166.6`，会落到第 3331 行（166.55 s）——早一行。取 `ε = 1e-6` 秒（远小于 `dt = 0.05`，远大于浮点误差）。N 很大时可用二分查找；`find(...,1,'last')` 对 12000 行已经够用（本机整次 `SeekFrame` 含重绘实测 6–11 ms/行，主要时间在绘图而不在查找，所以不要提前优化）。

### 4.2 边缘检测（层 5）

几乎所有事件都是“某列的值和上一行不同”：

```text
changeRows(x) = { r ≥ 2 : x(r) ≠ x(r−1) }          % 注意从第 2 行开始
```

向量化写法是 `find(x(2:end) ~= x(1:end-1)) + 1`。**偏移一格最容易错**：差分的第 i 个元素对应原数组的第 i+1 行。

三个变体：

- **起点型**：只要“进入某种状态”的那一行。例如请求种类∈{Kick,Search,Tap} 且（种类变了 **或** 编号变了）。
- **去重型**：反馈。机器人空闲时 `status` 会保留旧终态，所以要看 `(status, feedbackId)` 这一对是否变化，且 `status ∈ {Done, Failed, Rejected}`。
- **逐行型**：`kicker ≠ 0` 的每一行是一次踢球。一开始我用“上升沿”，结果漏掉了相邻两步分别由两个机器人踢的情况（122 对 126）——**踢球只持续一步**，所以不能合并。

### 4.3 “推断”事件：游程编码（层 5）

“追球者连续不动 ≥ 1 s”要找**连续成立的区间**。令 `still(r)` 为真当且仅当：追球者编号 > 0、其世界速度 `hypot(vxw, vyw) < 0.02` 且 `running ≠ 0`。区间必须在**追球者换人时断开**——否则两个机器人的静止会被并成一段。定义“第 r 行接续第 r−1 行”：

```text
link(r) = still(r) ∧ still(r−1) ∧ chaser(r) = chaser(r−1)
起点 = { r : still(r) ∧ ¬link(r) }
终点 = { r : still(r) ∧ ¬link(r+1) }
```

起点与终点按顺序一一配对；时长 = `times(终) − times(起) + dt`，大于阈值才报告。这是**规则推断**，要标 `inferred`，并写明规则与阈值。

### 4.4 检查器文字（层 3 的一部分）

每个数字都是记录值或其单位换算：速度 = `hypot(vxw, vyw)`；枚举值用工程自己的枚举类翻译成名字。**不要在回放里再保存一份“1=Goto, 2=Kick”的表**——枚举一旦修改，两份就会不同步。不认识的值显示成数字，不要猜。

## 5. 播放索引与时间映射（层 4）

用“锚点”模型，而不是“每个 timer 周期加一个增量”：

```text
t_play(now) = min( t_end ,  a + r · (now − τ0) )
frame       = k( t_play )
```

`a` 是锚定的仿真时间，`τ0` 是锚定的墙钟，`r` 是速度倍率。为什么这样设计：

1. **timer 不准。** MATLAB 的 timer 周期是“尽量”，繁忙时会晚。“每次加固定增量”会让回放越来越慢；锚点模型每次都从墙钟重新算，只是显示晚一点。
2. **暂停、换速、跳转都变成同一件事——重新锚定**：
   - 暂停：`a ← t_play(now)`，停 timer。
   - 继续：`τ0 ← now`，启 timer。
   - 换速：`a ← t_play(now)`，`τ0 ← now`，再改 `r`。（如果先改 r 再锚定，当前时刻会瞬间跳变。）
   - 跳转：`a ← times(目标行)`，`τ0 ← now`。
3. **8× 时会跳行。** 每 40 ms 前进 0.32 s 即约 6 行，显示的是“不晚于当前时间的最近一行”。这是预期；需要逐行请用单帧。

边界：到最后一行就停 timer、禁用“继续”、状态写“回放结束”；从头播放回到第 1 行并重新锚定。

## 6. 速度与跳转（层 4 的细节）

- 速度只能取固定档位，并校验；非法值抛错而不是取整。
- 单帧步进 = 先暂停（重新锚定到当前行），再 `frame ± n` 夹在 [1, N] 内，再 `a ← times(frame)`。
- 数值输入框跳转要做输入校验：非数字**忽略并提示**，不要抛未处理异常。
- 按键处理要**避开输入框**：用户在输入框里敲数字时，`[`、空格不应触发快捷键。

## 7. 状态与事件的渲染（层 3、5）

- 把“当前行 → 文字”写成一个纯函数（输入一行物理数据和一行战术数据，输出字符串数组）。纯函数能直接断言，不需要开窗口。
- 把信息按**来源层**分栏：记录的真值 / 决策（意图、阶段、追球者）/ 请求 / 反馈。分栏本身就是在回答“这是谁说的”。**“意图”和“请求”不是一回事**：意图来自球队协调器，请求是授权之后真正交给执行器的；被撤权的意图会变成 Stop 请求。
- 事件列表每行带来源标记：`[R]` 记录值的变化，`[I]` 推断。**`[R]` 也不代表原因**：`phase Attack → Fallback` 只说明字段变了。
- 选中项 = 行号不超过当前行的最后一个事件，用 `find(eventFrames <= frame, 1, 'last')`。

## 8. 视频导出设计（层 6）

**设计原则：按行号渲染，不按墙钟。**

```text
rows = first : Stride : last                 % 选定区间内的记录行
对每个 k：显示行 rows(k) → 抓取窗口 → 存 PNG
ffmpeg 以 FrameRate 把 PNG 序列编成 H.264
视频时间(k) = (k−1)/FrameRate
仿真时间(k) = times(rows(k))
倍速 = dt · Stride · FrameRate               （=1 为实时）
```

为什么不用实时录屏：录屏拿到的是“某个时刻 MATLAB 恰好画到哪一行”，视频时间和仿真时间的关系依赖机器负载，无法复现；而且会录进无关窗口。按行渲染则每一帧对应哪一行是确定的，可以写成 CSV。

实现要点：

- 抓取窗口用 `getframe`。`print` 会拒绝含 UI 控件的窗口；本机 `VideoWriter` 没有 MPEG-4 档，所以用 PNG 序列 + ffmpeg。
- H.264 的 `yuv420p` 要求宽高为偶数；窗口尺寸不保证，加 `scale=trunc(iw/2)*2:trunc(ih/2)*2`。
- 从 MATLAB 调 `ffmpeg` 要清掉 `LD_LIBRARY_PATH`/`LD_PRELOAD`，否则 MATLAB 自带库会与系统 ffmpeg 冲突。用 `shellQuote` 之类的函数给路径加引号：路径里有空格和 `&`。
- 先检查 ffmpeg 可用，再渲染；失败要清理临时帧、不留半成品视频、给出 ffmpeg 的错误输出。
- 不覆盖已有文件（除非显式允许）；扩展名必须是 `.mp4`。

## 9. 重要的边界情况

| 情况 | 期望行为 |
|---|---|
| 只有 1 行的记录 | 滑块禁用，不崩溃 |
| 时间不严格递增 | 拒绝，指出原因 |
| 含 NaN | 拒绝 |
| 列数不是 98 | 拒绝，不猜 |
| `tactics` 行数/时间不一致 | 降级为“无战术信息”并警告，位置照常显示 |
| 无 `tactics`（旧策略） | 检查器写明“NOT RECORDED”，事件仍有进球、踢球 |
| `seekTime` 在第一行之前/最后一行之后 | 夹到第 1 行/最后一行 |
| 对结尾继续“继续播放” | 不做任何事 |
| 事件为空 | 列表显示占位并禁用 |
| 输出文件已存在 | 拒绝覆盖 |
| 导出区间无帧 | 报告记录的实际时间范围 |

## 10. 常见错误（有些是开发中真的犯过的）

1. **差分偏一格。** `diff` 的第 i 个元素对应第 i+1 行。
2. **用 `==` 比较浮点时间。** 见 §4.1。
3. **把“请求编号变了”当成“发出了新动作”。** Goto 每一拍都换编号，要先限定种类。
4. **把反馈当成“刚发生”。** 反馈会保留旧终态，必须按 `(机器人, 编号)` 去重。
5. **把踢球合并成上升沿。** 相邻两步可能分别由两个机器人踢。
6. **混用全局号和本地号。** `tactics` 的追球者是全局号 1–8，物理记录第 71–72 列是本地号 1–4。
7. **时钟在窗口首次绘制完成之前就开始走。** 首次绘制可能耗时数秒，回放的开头被吃掉。先 `drawnow` 再开始计时。
8. **在 timer 回调之外修改了只在回调里更新的状态**，导致暂停后时间“补跳”。所有状态变化走同一组函数。
9. **把推断当记录。** 凡是“由阈值得出”的都标 `inferred`。
10. **信任文件名。** 不要从文件名推断内容，读 `whos`。

## 11. 调试方法

1. **先在 Python 里独立算一遍。** 用 `scipy.io.loadmat` 读同一个 `trace.mat`，写十行 numpy 数出“阶段变化几次、踢球几行、接管几次”。MATLAB 的结果必须一致（本参考实现就是这样确认 22/44/126/1/1/107 的，见 `phaseC/independent_counts.py`）。两种语言、两份代码得到同一数字，比单边断言可信得多。
2. **用合成数据，把答案先写在纸上。** 造 80 行全零矩阵，只在第 10 行改一个值，事件必须恰好出现在第 10 行。
3. **二分定位。** 事件时间不对时，打印 `[行号, 时间, 该列值]` 三列，看相邻行。
4. **窗口问题用 `getframe` 存 PNG 看。** 不需要显示器，隐藏窗口也能截图（第一次调用会慢几秒）。
5. **计时问题把 `State()` 打印出来**，比盯着窗口可靠。

## 12. 建议的实现顺序（每步都能独立验证）

| 步 | 做什么 | 验证（你自己写） |
|---|---|---|
| 1 | 载入与校验函数 | 对 6 种坏文件各给一个明确错误；对真实记录返回正确尺寸 |

## 13. 如何验证每个组件（以及怎样证明是你自己的）

- 每个组件配一个测试，**先写测试再写实现**：测试用的数据（合成矩阵）要自己造，答案要在运行之前写好。
- 把你的实现和参考实现在同一批输入上并排运行：事件列表逐项比较，`State()` 序列比较，导出视频的对照表逐行比较。**不一致不一定是你错**——参考实现也可能有缺陷，每处差异都要查明并写下原因。
- 用不同于参考实现的设计也可以（例如二分查找、`table` 表示事件），只要通过同一套行为测试。

## 14. 不要照抄的地方

参考实现的下面这些选择是**取舍**，不是必须：窗口 1600×800 的布局、1 µs 的容差、0.02 m/s 与 1 s 的阈值、PNG+ffmpeg 的导出路径。你可以改，但要能说出理由，并让测试反映你的选择。
